# Persistent Memory App — Project Spec

## What this is

A local-first personal memory app. The user writes details about their life (notes,
facts, events, preferences), the app stores them, and later the user can ask
natural-language questions about what they've stored. Answers are generated by a
locally-run language model using retrieval over the stored memories (RAG), not a
cloud API.

Inspired conceptually by "EgoMem" style lifelong memory agents, but starting far
simpler: manual text entry only, on a laptop, before any mobile or multimodal work
begins.

## Current stage: Phase 1 prototype

Goal: prove the core loop works well enough to demo to a university supervisor as a
project pitch. This is NOT the mobile app yet. It runs entirely on a laptop.

Core loop to prove:
1. User types a memory ("I have a dentist appointment on the 14th", "My brother's
   name is Ali", "I prefer tea over coffee").
2. The app stores it.
3. User later asks a question ("when is my dentist appointment?", "what does my
   brother like?").
4. The app retrieves the relevant stored memory/memories and generates a correct,
   grounded answer using a local LLM.

## Target platform for the prototype

Python, running locally. A simple web UI (Streamlit or Gradio) is preferred over a
bare CLI script, since this will be demoed live to a supervisor — it should look and
feel like a small product, not a terminal script. A CLI fallback is acceptable if
the UI framework causes setup friction, but the UI is the target.

## Architecture (applies now and later — do not violate this shape)

Every piece of input, regardless of source, becomes a "memory record" with:
- raw text (the memory content, or a transcript/description if it originated from
  audio/video in later phases)
- an embedding vector (for semantic search)
- a timestamp
- a source-type tag (phase 1: always "text")

This normalization is intentional. Phase 1 only ever produces source-type "text",
but the storage and retrieval layers should be written as if other source types
could exist, so later phases (see Roadmap) only require adding new capture
adapters, not rewriting storage/retrieval/generation.

### Layers

1. Capture layer
   - Phase 1: a text input box where the user types a memory and submits it.
   - No ML happens here. It just hands raw text to the storage layer.

2. Storage layer
   - Persist memory records: text, embedding, timestamp, source-type.
   - Phase 1 scale is small (hundreds to low thousands of entries), so a simple
     local store is sufficient: SQLite, or even a JSON/pickle file, holding text +
     embedding vectors together.
   - No need for a dedicated vector database at this scale. Brute-force cosine
     similarity search over stored embeddings (numpy) is fine and preferred for
     simplicity.

3. Retrieval layer
   - On a question, embed the question using the same embedding model used for
     stored memories.
   - Compute similarity against all stored embeddings, return the top-k most
     relevant memory records (start with k=3-5, make it configurable).

4. Generation layer
   - Feed the retrieved memory records plus the user's question into a locally
     running LLM as context, and have it generate a natural-language answer
     grounded in that context.
   - The model must run locally, not via a cloud API. Use Gemma (a small variant
     suited to local/on-device use) served via Ollama for the prototype, since
     Ollama handles quantization and serving with minimal setup. llama.cpp or
     transformers direct-loading are acceptable alternatives if Ollama causes
     environment issues, but Ollama is the default choice.
   - For embeddings, use a small local embedding model (e.g. a sentence-transformers
     model, or Gemma's embedding variant if available via Ollama). It does not need
     to be the same model as the generation model.

## Explicit non-goals for Phase 1

- No mobile app yet (Android work comes after this prototype validates the
  chunking/retrieval/generation approach).
- No audio, video, or smart-glasses input yet.
- No cloud model calls — everything must run locally, since the end product is
  meant to be local-first/private.
- No user accounts, sync, or multi-device support.
- No need for a production-grade vector database — brute-force search is
  intentional and sufficient at this scale.

## Roadmap (for context only — do not build these yet)

- Phase 2: Audio input. On-device speech-to-text produces a transcript, which is
  then treated as a normal text memory record (source-type "audio").
- Phase 3: Video/image input. An on-device vision-language step produces a text
  description of the frame/video, then treated as a normal memory record
  (source-type "video").
- Phase 4: Smart glasses as a capture device, streaming to the phone (likely over
  Bluetooth). Capture location changes; storage/retrieval/generation architecture
  should not need to change if Phases 1-3 were built correctly.
- Eventual port: once the retrieval + prompting approach is validated on the
  laptop, the same architecture gets reimplemented as an Android app (Room for
  storage, MediaPipe LLM Inference API with a quantized Gemma .task model for
  on-device generation, an on-device embedding model, and brute-force or
  lightweight local vector search).

## Success criteria for the prototype demo

- User can add several memories through the UI.
- User can ask a question in natural language and get back an answer that is
  actually grounded in a previously stored memory (not hallucinated).
- The retrieval step is visibly working (e.g. it's fine, even useful for the
  pitch, to show which stored memories were retrieved for a given question).
- Runs fully offline / locally once models are pulled.
