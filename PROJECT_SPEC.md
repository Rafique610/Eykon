# Persistent Memory App — Project Spec

## What this is

A local-first personal memory app. The user writes or speaks details about their
life (notes, facts, events, preferences), the app stores them, and later the user
can ask natural-language questions about what they've stored. Answers are
generated by a locally-running language model using retrieval over the stored
memories (RAG), not a cloud API.

Inspired conceptually by "EgoMem" style lifelong memory agents, built up in phases
starting from a text-only desktop prototype before moving to a native mobile app.

---

## Phase 1 Summary (Complete ✅)

Phase 1 validated the full capture → embed → store → retrieve → generate loop
as a Python desktop prototype with a Streamlit UI.

### Phase 1.0 — Core Pipeline
- Storage: SQLite + JSON-encoded embeddings, feature-based folder structure.
- Embeddings: `BAAI/bge-small-en-v1.5` (384-dim, 512-token window) via
  `sentence-transformers`.
- Retrieval: Hybrid search — dense cosine similarity + SQLite FTS5 BM25,
  merged with Reciprocal Rank Fusion (RRF).
- Generation: Gemma 4 E2B via LiteRT-LM on-device edge engine
  (`litert-community/gemma-4-E2B-it-litert-lm`, ~2.4 GB .litertlm format).
- Capture: Token-bounded chunking (256 avg, 30–50 overlap, 400 ceiling) with
  chunk metadata (chunk_index, total_chunks, token_count).
- UI: Two-page Streamlit app (📝 Add Memory · ❓ Ask Question), sidebar with
  live memory count, model status, demo tools.

### Phase 1.1 — Retrieval Quality Improvements
Benchmark: 499 memories (50 gold, 449 noise), 30 ground-truth QA pairs.

| Configuration               | Hit@1   | Hit@5   | MRR    | Avg Latency |
|------------------------------|---------|---------|--------|-------------|
| Baseline (Phase 1.0)         | 53.33%  | 76.67%  | 0.6500 | ~40 ms      |
| + Query Expansion (Step 09)  | 56.67%  | 86.67%  | 0.6900 | ~40 ms      |
| + Widen Pool to 20 (Step 10) | 63.33%  | 93.33%  | 0.7411 | ~45 ms      |
| + Cross-Encoder (Step 11)    | **76.67%** | **93.33%** | **0.8344** | ~1.2 s |

Final pipeline: Expand → Widen & Fuse (RRF) → Cross-Encoder Re-rank.
Exact factual queries: **100% Hit@1**. All three improvements enabled by default.

### Key Phase 1 Decisions (Locked)
- Embedding format: JSON-serialized string (debuggability over compactness).
- Repository pattern: Module-level functions (not class-based).
- Prompt style: Strict grounding — "answer ONLY from stored memories."
- Temperature: 0.1 (factual/deterministic).
- Cross-encoder: `cross-encoder/ms-marco-MiniLM-L-6-v2` (~80 MB).
- Query expansion: Static concept map (zero-latency dictionary lookup).

## Current stage: Phase 2 (Mobile + Audio)

Phase 1 (Python desktop prototype) is complete. It validated the full retrieval +
generation loop, including a hybrid dense/sparse retrieval pipeline with
query expansion, pool widening, and cross-encoder re-ranking, and generation using
Gemma 4 E2B via LiteRT-LM directly (not Ollama). Because LiteRT-LM is a
cross-platform runtime, the same model file format validated on desktop is the one
targeted on Android, which is the main reason Phase 2 carries real confidence into
the mobile port rather than starting the generation-layer risk from zero.

Phase 2 goal: port the validated architecture to a native, fully offline Android
app, and add voice as a second capture method.

### Core loop to prove in Phase 2
1. User types a memory, or taps record and speaks one.
2. If spoken, the audio is transcribed locally by Whisper (on-device).
3. The resulting text is embedded and stored as a memory record (source-type
   "text" or "audio").
4. User asks a question via text (or voice, if time permits).
5. The app retrieves relevant stored memories and generates a grounded answer
   using Gemma 4 E2B running on-device via LiteRT-LM.

---

## Target platform

Android (Kotlin). The app must run entirely locally on the device. All models
(Whisper for speech-to-text, the embedding model, and Gemma 4 E2B for generation)
run on-device. No cloud API calls at any point.

---

## Architecture (applies now and later — do not violate this shape)

Every piece of input, regardless of source, becomes a "memory record" with:
- raw text (the memory content, or a transcript if it originated from audio)
- an embedding vector (for semantic search)
- a timestamp
- a source-type tag ("text" or "audio" in Phase 2; "video" arrives in Phase 3)

This normalization is intentional. Storage and retrieval treat every memory
record identically regardless of source-type, so later phases only require new
capture adapters, not changes to storage, retrieval, or generation.

### Layers

1. **Capture layer**
   - Text input box (ported from Phase 1) or a voice record button.
   - Voice input is transcribed locally by Whisper (on-device, e.g. via a
     maintained Android/whisper.cpp wrapper) to produce a raw text transcript.
   - Once transcribed, an audio-sourced memory is handled identically to a
     typed one — same validation, same embedding call, same storage call.

2. **Storage layer**
   - Android Room (SQLite), mirroring the Phase 1 schema: id, text, embedding,
     timestamp, source_type, and the chunk metadata fields added in Phase 1.1.
   - Embeddings stored as a JSON-encoded string (matching Phase 1 for
     consistency and easy debugging).
   - Sufficient at Phase 2 scale (hundreds to low thousands of entries) — no
     dedicated vector database needed.

3. **Retrieval layer**
   - An on-device embedding model (kept within the LiteRT ecosystem for
     platform consistency, since LiteRT's native/FFI paths are the ones with
     confirmed Android support) embeds the question.
   - Brute-force cosine similarity search in plain Kotlin against stored
     embeddings. No NDK/C++ needed — at this scale (hundreds to low thousands of
     records) a Kotlin loop over an array runs in single-digit milliseconds.
   - Returns the top-k most relevant memory records (default k=5, configurable),
     matching Phase 1's tuned defaults.
   - Start with plain dense retrieval for the mobile port. If an accuracy gap
     shows up during testing on real questions, evaluate whether the Phase 1.1
     hybrid pipeline (dense + keyword fusion, cross-encoder re-ranking) is worth
     porting — this is a decision for the retrieval step, not assumed either way.

4. **Generation layer**
   - Gemma 4 E2B (~2.4GB, .litertlm format) running on-device via the
     LiteRT-LM Android (Kotlin) API.
   - **Not** the MediaPipe LLM Inference API, which is now in maintenance-only
     mode per Google's current guidance — LiteRT-LM is the actively supported
     path and the one already validated on desktop.
   - Prompt structure carries over from Phase 1: strict grounding instructions,
     numbered list of retrieved memories as context, explicit fallback
     instruction when no relevant memory is found.

## Explicit non-goals for Phase 2

- No video, image, or smart-glasses input yet.
- No cloud model calls — everything must run locally.
- No user accounts, sync, or multi-device support.
- No production-grade vector database — brute-force search is intentional and
  sufficient at this scale.
- No NDK/C++ for retrieval — plain Kotlin is sufficient and simpler.

---

## Key constraints and risks (confirmed, not just anticipated)

- **Model size:** Gemma 4 E2B is ~2.4GB. This must be downloaded on first launch
  (not bundled in the APK — Play Store's base app size limits rule that out
  regardless), stored in the app's external files directory, and verified with
  a checksum before the app considers setup complete. Use WorkManager for the
  download so it survives the app being backgrounded, and check available
  device storage before starting.
- **Architecture restriction:** LiteRT-LM's native/FFI inference paths (and
  on-device embedding via the same route) are commonly built for arm64-v8a
  only, not x86_64. This means the standard Android Studio emulator, which
  typically runs x86_64, may not run the model at all. Development and testing
  must happen on a real arm64 Android device from early in Phase 2, not saved
  for the final integration step.
- **RAM:** Budget for a genuinely capable test device. Published benchmarks for
  models in this size class show peak memory usage in the multi-gigabyte range
  during inference — a low-RAM device is likely to struggle or fail outright.

## Roadmap (for context only — do not build these yet)

- Phase 3: Video/image input. An on-device vision-language step produces a text
  description of the frame/video, then treated as a normal memory record
  (source-type "video").
- Phase 4: Smart glasses as a capture device, streaming to the phone (likely
  over Bluetooth). Capture location changes; storage/retrieval/generation
  architecture should not need to change if Phases 1–3 were built correctly.

---

## Success criteria for the Phase 2 prototype

- App installs and runs natively on a real arm64 Android device.
- User can add text memories and voice memories (transcribed on-device via
  Whisper).
- User can ask a question and get back an answer grounded in a previously
  stored memory (not hallucinated), generated completely on-device via
  LiteRT-LM.
- The 2.4GB Gemma model downloads on first launch with visible progress and a
  checksum check, and the app handles insufficient storage gracefully.
- Runs fully offline once setup (model download) is complete.
