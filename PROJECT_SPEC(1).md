# Persistent Memory App — Project Spec

## What this is

A local-first personal memory app. The user writes details about their life (notes,
facts, events, preferences), the app stores them, and later the user can ask
natural-language questions about what they've stored. Answers are generated by a
locally-run language model using retrieval over the stored memories (RAG), not a
cloud API.

Inspired conceptually by "EgoMem" style lifelong memory agents, but starting far
simpler: manual text entry only, on a laptop, before any mobile or multimodal work
begins.

## Current stage: Phase 2 (Mobile + Audio)

Goal: Phase 1 (Python desktop prototype) is complete. The core loop of local retrieval and generation is validated. We are now building Phase 2: transitioning to a local-first Android application and introducing Voice Input.

Core loop to prove in Phase 2:
1. User taps a record button and speaks a memory ("I have a dentist appointment on the 14th").
2. The app transcribes the audio locally using an on-device STT model (e.g., whisper.cpp).
3. The transcript is stored as a memory record (source-type: "audio").
4. User asks a question via text or voice.
5. The app retrieves the relevant stored memory and generates a grounded answer using an on-device quantized LLM.

## Target platform

Android (Kotlin). The app must run entirely locally on the mobile phone. All models (Speech-to-Text, Embedding, LLM) run on-device.

## Architecture (applies now and later — do not violate this shape)

Every piece of input, regardless of source, becomes a "memory record" with:
- raw text (the memory content, or a transcript/description if it originated from
  audio/video in later phases)
- an embedding vector (for semantic search)
- a timestamp
- a source-type tag (phase 1: always "text")

This normalization is intentional. Phase 1 only ever produces source-type "text",
but the storage and retrieval layers should be written as if other source types
could exist, so later phases (see Roadmap) only require adding new capture
adapters, not rewriting storage/retrieval/generation.

### Layers

1. Capture layer
   - Text input box or Voice Record button.
   - Voice input is processed locally by an STT engine (e.g., whisper.cpp or Vosk) to produce a raw text transcript.

2. Storage layer
   - Android Room (SQLite).
   - Persists memory records: text (transcript), embedding vector (stored as BLOB), timestamp, source-type ("text" or "audio").
   - At our scale (hundreds to low thousands of entries), a simple local store is sufficient.

3. Retrieval layer
   - MediaPipe Text Embedder (using a lightweight mobile model) embeds the question.
   - Brute-force cosine similarity search in Kotlin/C++ against all stored SQLite BLOB vectors. Returns the top-k most relevant memory records (start with k=3-5, make it configurable). No dedicated vector database needed.

4. Generation layer
   - Feed the retrieved memory records plus the user's question into a locally running LLM as context, and have it generate a natural-language answer grounded in that context.
   - The model must run locally on the phone, not via a cloud API. Use MediaPipe LLM Inference API running a quantized Gemma model (e.g., Gemma 2B int4) since it is optimized for Android GPU/NPU.

## Explicit non-goals for Phase 2

- No video, image, or smart-glasses input yet.
- No cloud model calls — everything must run locally, since the end product is meant to be local-first/private.
- No user accounts, sync, or multi-device support.
- No need for a production-grade vector database — brute-force search is intentional and sufficient at this scale.

## Roadmap (for context only — do not build these yet)

- Phase 3: Video/image input. An on-device vision-language step produces a text description of the frame/video, then treated as a normal memory record (source-type "video").
- Phase 4: Smart glasses as a capture device, streaming to the phone (likely over Bluetooth). Capture location changes; storage/retrieval/generation architecture should not need to change if Phases 1-3 were built correctly.

## Success criteria for the Phase 2 prototype

- App installs and runs natively on an Android device.
- User can add text memories and voice memories (transcribed on-device via STT).
- User can ask a question and get back an answer that is actually grounded in a previously stored memory (not hallucinated), generated completely on-device.
- App handles large model downloads (Gemma 2B) correctly or they are bundled appropriately.
- Runs fully offline / locally without relying on cloud APIs.
