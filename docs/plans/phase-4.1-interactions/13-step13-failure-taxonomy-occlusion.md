# Phase 4.1 Step 13 — Failure Taxonomy and Occlusion Analysis

## What

Explain every error from Step 12 (tuning and held-out), so the thesis can say
not only "how often" but "why" and "what would fix it":

- classify each false negative and false positive into a fixed taxonomy:

  | Code | Failure | Typical cause |
  |---|---|---|
  | `occluded_in_hand` | object hidden by fingers | small objects, closed grasp |
  | `occluded_by_scene` | object hidden by other objects or bag edge | put into bag, behind cup |
  | `out_of_view` | action outside the camera field | chest mount, low hands |
  | `too_small` | object too few pixels | ring, pill, SIM tool |
  | `look_alike` | confused with a similar object | two black wallets, keys vs coins |
  | `hand_not_found` | hand model missed the hand | dim light, sleeves, edge of frame |
  | `place_confusion` | wrong room or surface | similar rooms, dark surfaces |
  | `flicker` | false event from noisy identity | uncertain crops |
  | `timing` | right event outside the tolerance | slow release |
  | `other` | anything else, described | — |

- counts per code, per size class and per split (tuning / held-out),
- a gallery with 3–5 examples per code (privacy-checked frames),
- for each code: is it fixable within the project (and by which step or
  phase), or a fundamental limit of a single body-worn camera?

## Why

- The handoff and roadmap require failure reporting, not only averages; the
  panel will ask about small and hidden objects.
- Separating fixable failures from fundamental limits makes the
  "future work" section concrete and stops over-promising.
- Occlusion is the expected main failure; counting it precisely turns a weak
  point into an honest, well-understood finding.

## How to implement

1. **Error list** generated by `interaction_eval.py` (each error with session,
   time, object, predicted vs true, frames).
2. **Labelling** of each error with the taxonomy code in the Phase 3.1
   labelling page (a new mode); a second person labels 20 % for agreement.
3. **Tables and gallery** generated by script.
4. **Fixability column** written by the user and agent together.
5. **Cross-reference**: which failures the VLM path also has (input to
   Step 14).

## Open decisions

- **One code per error or several.** Options: (a) one primary code —
  simple counts; (b) multiple codes — more accurate, counts no longer add up;
  (c) one primary plus optional secondary. Draft: (c).

## You test this

1. Label 20 errors yourself; time how long it takes.
2. For the top three failure codes, decide whether you would spend project
   time fixing them, and why.

## How this number could be lying

- The labeller knows the system and may favour "fundamental limit" codes
  over "our bug" codes. The second labeller and the agreement number check
  this.
- Galleries show the most striking failures; counts are what matter.
