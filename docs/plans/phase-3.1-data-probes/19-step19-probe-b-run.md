# Phase 3.1 Step 19 — Probe B Run: Cheap Path vs VLM on Pick-Up and Put-Down

## What

Run both paths on the same sessions and score them against the Step 10
annotations, as pre-registered in Step 13:

- **Cheap path**: the Step 18 prototype on the 10-minute keys recording and
  all other state-change script sessions (except the session used for
  tuning).
- **VLM path**, in the configurations chosen in Step 13's open decision:
  - VLM-fixed: Gemma 4 E2B slot prompt on frames at a fixed rate,
  - VLM-triggered: Gemma 4 E2B slot prompt only on frames where the hand
    model fired (equal triggers),
  turned into events by the same rule used for the cheap path (object
  appears in hand / disappears), so the event logic is not what differs.
- **Scoring** `src/probes/probe_b.py`: match predicted events to annotated
  events (same object, same verb, time within the pre-registered
  tolerance); compute precision, recall, object identity accuracy, place
  accuracy for put-downs, with 95 % Wilson intervals; report separately for
  visible / partly visible / not visible annotated events and per object
  size.
- **Cost**: per minute of video, for each path: total compute time, model
  calls, peak memory (laptop, emulation profile).
- Report: `docs/results/phase-3.1/probe-b-report.md` with the verdict
  against the pre-registered viability rule.

## Why

- Probe B decides the scope of Phase 4.1 (Gate 1). If the cheap path is
  viable, the project can show an LLM-free route for object memory (L0 in
  Phase 5.2). If it is not, Phase 4.1 shrinks to this negative result, which
  is still a defensible finding.
- Using the same event rule for both paths isolates the question that
  matters: is the hand-crop + embedding perception as good as the VLM's
  perception, at what cost?
- The VLM-triggered variant tests a likely real design: cheap triggers,
  expensive model only when needed. That is relevant to Phase 4 regardless
  of who wins.

## How to implement

1. **Freeze**: confirm Step 18 thresholds and the pre-registration are
   committed before any scored run.
2. **Run** the cheap path and both VLM variants on all scored sessions; all
   outputs are slot records in `data/probes/b/<path>/<session>.jsonl`.
3. **Matching**: greedy one-to-one matching by time within tolerance, same
   object and verb; unmatched predictions are false positives, unmatched
   annotations are misses. The matching function is shared and later reused
   by Phase 4.1 Step 05.
4. **Tables** (generated by script, never typed):
   - main table: path × (precision, recall, identity accuracy, place
     accuracy) with intervals, keys recording only and all scripts;
   - by visibility; by object size;
   - cost per minute;
   - pre-registered verdict.
5. **Failure taxonomy** for the cheap path: `hand_not_found`,
   `object_confused` (which pairs), `occluded_in_hand`, `too_small`,
   `flicker_false_event`, `put_down_missed`; same for the VLM path where it
   applies. 10 examples each in a gallery.
6. **Sanity baseline**: a trivial "always predict the most common object at
   every hand appearance" baseline, to show the numbers are above chance.

## Open decisions

- **Tolerance** if Step 10 agreement shows human timing disagreement wider
  than ±2 s: follow the Step 10 rule (widen to the measured disagreement,
  documented), or report at two tolerances.
- **EPIC-KITCHENS as an extra test.** Options: (a) skip — our sessions
  only, as pre-registered; (b) add EPIC take / put events as an exploratory
  second test — independent annotations, different camera and objects;
  (c) add it only if the main result is "unclear". Exploratory runs are
  labelled as such in any case.

## You test this

1. Before reading the tables, watch the debug contact sheets for the keys
   recording for both paths side by side, and write your own guess: which
   path did better? Then read the table. If your impression and the numbers
   disagree, look for why.
2. Look at three cheap-path misses on visible events. Could anything cheap
   have caught them?
3. Read the verdict and the cost table. Would you be happy with the cheap
   path on your own phone for a day, given these numbers?

## How this number could be lying

- Object vocabularies are small (3–5 objects per session); matching among 5
  names is far easier than among 50. Report vocabulary size with every
  number; a stress run with an enlarged vocabulary (all objects from all
  sessions) is added as an exploratory check.
- Announced moves (speech) are not used by either path, but the user's
  movements during announcing may be more deliberate than natural moves.
  Results are split by `announced` (Step 10).
- The VLM event rule (appears / disappears in hand) is designed for the cheap
  path; the VLM might do better with a rule suited to captions. Noted as a
  limitation; Phase 4.1 Step 06 revisits it.
- At least 30 visible events are required by the pre-registration; if fewer
  exist, the report says so and the verdict is "unclear".

## Common issues

- The VLM-fixed variant is slow on a full session at 3 fps; use the
  pre-registered fixed rate (e.g. 1 fps) and report it.
- Event matching edge cases: a pick-up and put-down of the same object
  within 2 seconds. Match by order inside the tolerance window.
- Different frame timestamps between the phone capture app and the normal
  video recording: score against the clock used for annotation (Step 06 clap
  sync).
