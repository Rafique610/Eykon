# Phase 3.1 Step 12 — QA Set v2 and Tuning / Held-Out Split

## What

Write the question-and-answer set that every later phase is scored on:

- at least **30 questions per category** for all 11 categories from Step 01
  (at least 330 questions) on the **tuning** sessions,
- each question with: id, category, sub-tags (difficulty, time reference,
  object size, modality, scripted, planted), session id, the time at which
  the question is "asked" (questions like "where are my keys now?" depend on
  when they are asked), the gold answer, accepted synonyms, gold evidence
  time ranges, and who wrote it,
- a frozen **split file** listing which sessions and questions are tuning
  and which are held-out (held-out questions are written later, in Phase 4
  Step 12 and Phase 5.1, but the held-out sessions are fixed now),
- a QA validator and a loader in `src/scenarios/qa.py`,
- a converter that turns the old Phase 1 QA format (`src/benchmarks/data.py`
  `QA_PAIRS`) into the new format, so Phase 1 text questions can still be
  run with the new scorer.

This step replaces the QA part of the old Phase 4 Step 01 (which targeted at
least 150 pairs with at least 15 per category).

## Why

- The pessimist rule says no conclusion from fewer than 30 questions per
  condition (roadmap §5.1). Per-category reporting means 30 per category,
  not 30 in total.
- The "asked at" time is new and important: "where are my keys?" has a
  different correct answer at 10:05 and at 10:40. Without it, state questions
  cannot be scored.
- Gold evidence ranges allow scoring retrieval (did the system find the right
  moment?) separately from answering (did it say the right thing?), which
  Phase 5.2 needs to show where an LLM helps.
- Who wrote each question matters: questions written by the person who
  tunes the system leak knowledge. Recording authorship lets us report
  results for user-written and other-written questions separately.

## How to implement

1. **Sources of questions**, per category:
   - Object categories: generated drafts from `state_changes` and
     `short_events` (e.g. for every move, "where was X at time t?"), then
     edited by a human so they sound like real questions; not all
     auto-generated drafts are kept.
   - `temporal_order`, `activity_summary`: from `events`.
   - `conversation_recall`, `who_said`, `action_items`, `meeting_summary`:
     from meeting transcripts and references; AMI questions are allowed
     but tagged `source: public:ami`.
   - `lecture_recall`: from the lecture transcript and slides.
   - `negative`: objects in the vocabulary that never appear in that
     session, and events that never happened ("did I call mum?").
2. **Authors**: target at least a third of questions written by someone
   other than the user (a friend, a classmate, or the supervisor), from
   watching or listening to sessions, without seeing the system. Tag
   `author: user / other / generated-edited`.
3. **Format**: `data/scenarios_v1/qa_v2.json`, one object per question.
   Validator checks: category and sub-tags valid, session exists and is a
   tuning session, asked-at time inside the session, gold evidence inside the
   session and outside `exclude` ranges, gold answer place or object in the
   vocabulary.
4. **Counts table** generated by `task qa-status`: questions per category ×
   sub-tag × author × source. Committed to `docs/results/phase-3.1/qa-status.md`.
5. **Split file** `data/scenarios_v1/split_v1.json`: lists tuning and
   held-out sessions (from the manifest), plus a hash of the tuning
   question file at the time of freezing. The hash of the split file itself
   is written into `docs/results/phase-3.1/qa-status.md` (committed), so
   later changes are detectable.
6. **Phase 1 converter**: `QA_PAIRS` from `src/benchmarks/data.py` become
   questions in category `text_recall` (an extra category for Phase 1
   compatibility, not counted in the 11), so the old benchmark can run
   through the new scorer and the numbers can be compared with Phase 1's
   Hit@5 93.33 % and MRR 0.8344.
7. **Freeze**: once counts are met, the tuning QA is frozen (version
   `qa_v2.0`). Later edits create `qa_v2.1` with a changelog; results always
   state which version they used.

## Open decisions

- **Questions per session cap.** Options: (a) no cap — the richest sessions
  dominate; (b) cap per session (e.g. at most 15 % of a category from one
  session) — more representative, may make 30 per category harder to
  reach; (c) no cap, but report per-session results so dominance is visible.
- **Wording variety.** Options: (a) one wording per fact — simple;
  (b) two wordings for 20 % of questions — measures robustness to phrasing,
  which matters for embedding search; (c) paraphrases only in a separate
  robustness set. Option (b) costs little and answers a real question.
- **Free-form vs structured gold answers** for summary categories: decided by
  Step 01 scoring rules (human judgement), so gold answers there are
  reference bullets, not a single string. No separate decision needed unless
  Step 01 changes.

## You test this

1. Read 20 random questions (from `task qa-sample -- 20`). Mark any that you
   would never actually ask in real life. Those get rewritten.
2. Answer 10 random questions yourself from memory, without looking at the
   recordings. If you can answer them all easily, they may be too easy; if
   you cannot answer any, they may be unfair.
3. Check the counts table: does every category reach 30? Which sub-tags are
   thin (e.g. small objects in dim light)?

## How this number could be lying

- Auto-generated questions from annotations are easier for a system that
  reads the same annotations' structure (for example a state table). The
  `author` tag lets results be reported for human-written questions only.
- 30 questions per category can still be 30 near-identical questions about
  the same keys. The counts table shows objects and sessions per category.
- Planted facts in meetings make questions easier. Tagged and reported
  separately.

## Common issues

- Questions that need two sessions ("did I take the keys before or after
  the meeting?") break the one-session field. Allow a list of sessions, and
  tag them `cross_session: true`.
- Vague questions ("what happened?") cannot be scored. Every question must
  have a gold answer someone else could check.
- Running out of `negative` questions that are plausible: use the
  vocabulary of objects that appear in other sessions but not this one.
