# Phase 3.1 Step 16 — Probe A Analysis: Invention and Miss Rates

## What

Label the Step 15 outputs blind with the Step 14 page, then compute and
report:

- invention rate and miss rate, overall and per object size × lighting cell,
  with 95 % Wilson intervals, per model and prompt,
- wrong-attribute rate (object exists but colour, place or state is wrong),
- slot prompt vs free caption prompt on the same frames (paired
  comparison),
- JSON parse failure rate,
- whether the VLM's confidence (as defined in Step 02) predicts correctness
  (a simple table: accuracy in low / medium / high confidence bins),
- cost per frame (laptop, emulation profile),
- labeller agreement (kappa) on the double-labelled 20 %,
- the comparison with the pre-registered thresholds: acceptable, unclear or
  unacceptable,
- a failure gallery: the 10 worst inventions and 10 worst misses with
  frames.

Output: `docs/results/phase-3.1/probe-a-report.md` plus the CSV tables
behind it.

## Why

- This is the first measured answer to "can a small VLM be trusted as the
  source of object memory?" It decides whether the VLM path (L3 in Phase 5.2)
  can write directly into the state table, or only as low-confidence
  captions that need confirmation.
- Per-cell numbers show **where** it fails (small objects in dim light are
  the expected weak cell). An overall average would hide exactly the cases
  the user cares about (keys, rings, pills).
- The paired slot vs caption comparison tells Phase 4 Step 09 which output
  form to build on.
- Calibration of confidence tells Phase 5 Step 07 whether confidence can be
  used to decide when to trust a state change.

## How to implement

1. **Labelling**: truth pass on all frames, then output pass, per the
   Step 14 flow. Second labeller on the fixed 20 % subset.
2. **Analysis script** `src/probes/probe_a_report.py`: reads labels and
   outputs, computes all rates with intervals, writes CSVs and the markdown
   tables. No numbers are typed by hand into the report; the script writes
   them (real data only rule).
3. **Paired comparison**: for each frame, compare slot vs caption
   correctness; report how many frames each one gets right that the other
   gets wrong (a simple 2×2 table). A McNemar test (a standard test for
   paired yes/no outcomes) can be added with the standard library if the
   numbers are close; otherwise the table is enough.
4. **Threshold check**: an explicit section quoting the pre-registered
   thresholds and the measured values side by side, and the verdict.
5. **Failure taxonomy**: classify each invention by likely cause:
   `look_alike` (keys vs coins), `context_guess` (desk → "a laptop"
   that is not there), `blur`, `dark`, `occluded`, `other`. Each miss by:
   `too_small`, `occluded`, `dark`, `blur`, `out_of_centre`, `other`.
6. **Exploratory section** (clearly labelled as not pre-registered): any
   extra analysis that looks interesting after seeing the data.
7. **How this number could be lying** section written into the report
   itself (copied and extended from this doc).

## Open decisions

- **What to do with an "unclear" result** (interval overlapping the
  threshold). Options: (a) label 60 more frames from the same cells, once,
  as pre-allowed in Step 13's stopping rules — more certainty, more time;
  (b) treat "unclear" as "unacceptable" for safety — conservative, may drop
  a usable path; (c) carry it to Gate 1 as unclear and let the supervisor
  decide with the cost numbers. The pre-registration should already say
  which; if it does not, choose before labelling starts.

## You test this

1. Label all frames (this is the main work of the step). Write down how long
   it took.
2. Read the failure gallery. For each of the 10 worst inventions, would that
   mistake have made "where are my keys?" wrong? Mark yes or no; this is the
   user-impact column.
3. Read the verdict section. Do you agree with it, given the gallery?

## How this number could be lying

- 120 frames from our own rooms describe our rooms. Results are framed as
  "on our recordings", not as general VLM behaviour.
- The labeller is the user, who built the system. Blinding and the second
  labeller's kappa are the evidence that labels are not biased; if kappa is
  low (below about 0.6), this is reported prominently.
- Invention rate per object mention can look low if the model mentions many
  correct large objects (walls, tables). Also reported: invention rate on
  vocabulary objects only.
- Laptop VLM at 640×480 may be better or worse than the phone's runtime with
  the same file. Step 22 checks a subset on the phone.

## Common issues

- Frames in the gallery show participants or private items: blur or crop
  before committing; privacy rules (Step 03) apply to result files too.
- Disagreement on "wrong_attribute" vs "invented" (a "blue" bag that is
  black): the guide's rule is that the object exists, so it is
  wrong-attribute.
