# Phase 3.1 Step 21 — Probe C Run: Speech Recognition and Speaker Separation on Meetings

## What

Run the Step 20 speech stacks on the pre-registered meetings and score them:

- **Data** (from Step 13): the two Probe C meetings (one clean, one noisy)
  and at least 2 AMI meetings in the distant-microphone condition (headset
  condition as an upper bound if chosen in Step 04); at least 30 minutes per
  condition.
- **Pipeline**: audio → VAD → ASR (each shortlisted size) → speaker
  embeddings per segment → clustering → speaker labels → "me vs others" by
  comparing with the enrolment sample.
- **Metrics**:
  - WER (word error rate) overall, per condition, per speaker, with
    `[unclear]` words excluded as defined in Step 11;
  - DER (diarization error rate) with a 0.25 s collar, split into missed
    speech, false alarm and speaker confusion; also DER on overlapping
    regions only;
  - "me vs others" accuracy (share of speech time correctly labelled as the
    user or not), per condition and placement (table / body);
  - speaker count error when the number of speakers is estimated;
  - real-time factor and peak memory per stage (laptop, emulation profile);
  - a **downstream check**: for the `who_said` and `conversation_recall`
    questions on these meetings (Step 12), could the right answer be found
    in the transcript at the right time with the right speaker? (a simple
    lookup, no answer model) — this links the error rates to user impact.
- Report `docs/results/phase-3.1/probe-c-report.md` with the verdict against
  the pre-registered thresholds.

## Why

- Probe C decides Phase 5.1's depth (Gate 1): full "who said what", "me vs
  others" only, or low-confidence speaker labels.
- Splitting by condition and placement tells Phase 5.1 and Phase 6 how to
  advise the user (for example "put the phone on the table for meetings")
  instead of claiming one number for all situations.
- The downstream check stops a common trap: a WER that looks bad may not hurt
  the questions people ask (filler words), and one that looks fine may
  still garble the names and numbers that matter.

## How to implement

1. **Runner** `src/probes/probe_c.py`: for each meeting × stack, run the
   pipeline using the `src/speech/` wrappers, write outputs as RTTM plus
   transcript JSON (same formats as the references) and speech slot
   records (`kind: speech`), resumable, with timings.
2. **Scoring**:
   - WER: word alignment by edit distance after a fixed text normalisation
     (lower case, punctuation removed, numbers written one way). Written
     with the standard library; or a small well-known package only if the
     user approves.
   - DER: standard definition with collar; a reference implementation exists
     in `pyannote.metrics` (licence to verify); if not added, our own
     implementation is checked against a hand-computed toy example.
   - Speaker mapping: optimal one-to-one mapping between predicted clusters
     and reference speakers (Hungarian method — `scipy` if already
     available, otherwise a brute force over permutations, fine for at most
     4–5 speakers).
3. **Number of speakers**: run both known-count and estimated-count
   settings if Step 20's open decision chose (c).
4. **Tables** generated by script: per stack × condition × metric with
   intervals where the metric is a rate over items; per speaker; overlap
   only; cost; downstream lookup; verdict.
5. **Failure listening list**: 10 worst segments (highest confusion or WER)
   with timestamps so the user can listen to them.

## Open decisions

- **Overlapping speech in WER.** Options: (a) exclude overlap regions from
  WER — cleaner number, hides a real problem; (b) include them — honest,
  harder to interpret; (c) report both. Draft: (c).
- **If DER is "unusable" but "me vs others" is good**: options:
  (a) Phase 5.1 ships "me vs others" only; (b) Phase 5.1 adds a manual
  "name this speaker" step after the meeting to fix clusters (user effort,
  better results); (c) Phase 5.1 keeps speaker labels with visible low
  confidence. Recorded in the decision note (Step 23), not decided here.

## You test this

1. Listen to the 10 worst segments while reading what the system produced.
   For each, write one word: `noise`, `overlap`, `distance`, `accent`,
   `name`, `other`.
2. Pick 3 `who_said` questions from these meetings and check the downstream
   lookup yourself: can you find the answer in the system transcript?
3. Read the verdict and say whether, as a meeting participant, you would
   trust the speaker labels.

## How this number could be lying

- Two own meetings plus two AMI meetings is a small sample; numbers are
  reported per meeting so one bad meeting is visible, not averaged away.
- References were possibly pre-filled by a model (Step 09). The pre-fill
  model is excluded from the systems under test; if a tested model is
  related (same family, bigger size), it is stated.
- AMI's English speakers and our participants' accents differ; results are
  never merged into one number.
- Laptop real-time factor is not phone real-time factor; Step 22 measures
  the phone.

## Common issues

- 30-minute audio exhausts memory in some ASR wrappers if processed in one
  piece; process in VAD segments of at most 30 seconds.
- Clustering threshold tuned on the scored meetings would be cheating; tune
  on the pilot mini meeting (Step 05) or an AMI meeting not in the scored set.
- Time offsets between our transcript and the RTTM reference if audio was
  resampled with a different start; check with the clap sync.
