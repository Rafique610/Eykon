# Phase 3.1 Step 07 — Own Recordings: Objects and Daily Life (Pack A)

## What

Record the Pack A sessions defined in the Step 05 protocol: at least 3
hours across at least 6 sessions, at least 40 % unscripted, covering desk
work, tidying or kitchen, walking, leaving-the-house routines, low light, the
4+ state-change scripts (including the trap script), and one home
conversation with consent.

Each session ends with: raw files in the raw directory, the phone capture
folder (when the Step 06 app was used), a filled manifest row, the
"what happened that the script did not plan" note, and a split label.

Also record now, and lock away, the **held-out sessions** that Phase 4
Step 12 and Phase 5 evaluation will use: at least 2 sessions of about 20–30
minutes each in places not used for any tuning session. Nobody watches or
processes them until those steps.

## Why

- This is the main evidence base for Phase 4 (keyframes), Phase 4.1
  (interactions), Phase 5 (memory and state) and the object questions in
  Phase 5.2. Phase 3 had 3 stock clips of about 20 seconds; nothing defensible
  can be built on that.
- Recording held-out sessions **now** but not touching them is the cleanest
  protection against tuning to the test set: they exist before any threshold
  is chosen. (The old Phase 4 Step 12 planned to record them after tuning;
  both are honest, but recording now in different places is simpler and
  removes the risk of running out of time later. See open decision.)
- Probe B needs a specific **10-minute keys recording** with announced moves;
  it is one of the state-change scripts recorded here.

## How to implement

1. **Plan the calendar.** Spread sessions over different days and times
   (morning light, evening light), so the data is not one afternoon in one
   room. Fill a session plan table in `PROTOCOL.md`: date, session type,
   place, device, mount, scripted or not.
2. **Session order.**
   - First: the 10-minute **Probe B keys recording** (state-change script 1,
     Pixel, Step 06 capture app plus normal video). Probe B is unblocked as
     soon as it is annotated.
   - Then the remaining scripts and unscripted sessions.
   - At least one session per scenario type on the Infinix.
   - Held-out sessions in different rooms / places, recorded and immediately
     marked `split: heldout` in the manifest.
3. **After each session**, follow the checklist: copy, check playback, fill
   manifest, write the unplanned-events note, measure file size, run
   `task scenarios-validate`.
4. **Frames and audio extraction** (for later steps), by script, so it is
   reproducible: `task scenarios-extract -- <session>` writes
   `frames_1fps/` (for annotation and probes) and `audio_16k.wav` into
   `data/scenarios_v1/objects/<session>/`. Reuse `src/vision/extractor.py`
   (OpenCV, already in the project) rather than adding a new tool.
5. **Progress tracker.** A small table in `docs/results/phase-3.1/data-status.md`
   (generated by `task scenarios-status` from the manifest — not typed by
   hand, real data only): hours per session type, per device, scripted vs
   unscripted, tuning vs held-out, annotation status.
6. **Stop rule.** Stop recording Pack A when the minimum quantities are met
   or the time cap is reached (whichever rule the overview's open decision
   chooses).

## Open decisions

- **When to record the held-out set.** Options: (a) now, in different places
  (this draft) — guaranteed to exist, but recorded with the same habits as
  tuning data; (b) after tuning, as the old Phase 4 Step 12 planned — truly
  unseen conditions, risk of running out of time; (c) both: a small held-out
  set now and a second one later. (c) is the most defensible if time allows.
- **How long a "long" session should be.** Options: (a) 20–30 minutes —
  manageable annotation; (b) one 2-hour continuous session — tests drift,
  backlog and over-sampling properly, but annotation is heavy; (c) one
  2-hour session annotated only sparsely (state changes and coarse events),
  all others 20–30 minutes.

## You test this

This step is mostly you recording. Checks:

1. After the keys recording, watch it at 2× and confirm every announced move
   is visible on camera. If a move is not visible, note it — that is a real
   example of an occlusion failure, not a recording mistake.
2. After every session, run `task scenarios-validate` and
   `task scenarios-status`, and look at the status table.
3. At the halfway point, tell me which session types feel under-represented.

## How this number could be lying

- Hours recorded do not equal useful hours. A session where the camera
  pointed at the ceiling for 10 minutes is counted, but flagged in the
  manifest notes.
- One room dominating the data makes every later result room-specific. The
  status table shows hours per place.
- If held-out sessions are watched "just to check", they are no longer
  held-out. Only the file playback check is allowed, done by script.

## Common issues

- Audio extraction from video needs a decoder. OpenCV does not extract
  audio. Options: `ffmpeg` command line if already installed (check first),
  otherwise record audio separately with the Step 06 app. Do not add a
  Python audio library just for this without asking.
- Phones rotate video metadata. Check that extracted frames are upright.
- Long sessions drain the battery; plug in a power bank and note it in the
  manifest (it changes thermal behaviour).
